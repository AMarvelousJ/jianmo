## 1. 开发总原则

本项目第一阶段的开发目标不是做完整工业系统，也不是优先对接 PLC，而是先实现一个可信的装船机多自由度运动仿真内核。PRD 已明确第一阶段的核心是“装船机机构建模 + 多运动轴匀速运动 + 正运动学位姿计算 + 实时仿真状态输出”，PLC/HMI/API 都应围绕这个运动内核复用，而不是反过来主导内核设计。

因此，开发时必须遵守以下原则：

1. **能复用成熟库的地方，不自己重复造轮子。**
2. **核心业务必须自己掌控。**
3. **运动内核与可视化、API、后端框架解耦。**
4. **先保证计算正确，再追求界面效果。**
5. **先做 MVP，不提前陷入 PLC、联锁、碰撞检测、煤流等复杂模块。**

## 2. 技术选型与复用策略

### 2.1 后端框架复用策略

推荐使用 **FastAPI** 作为后端 API 框架，但第一阶段不要直接上复杂全栈系统。

FastAPI 官方文档明确提供多文件项目结构，并建议使用 `APIRouter` 将不同路由模块拆开，适合本项目后续把仿真命令、状态查询、配置管理、轨迹记录等接口拆分成独立模块。

FastAPI 官方还提供了 `full-stack-fastapi-template`，其技术栈包含 FastAPI、SQLModel、Pydantic、PostgreSQL、React、Docker Compose、Pytest、Traefik 和 GitHub Actions 等。这个模板适合后续需要账号、数据库、前端管理台、部署流水线时使用，但对当前运动仿真 MVP 来说偏重。

**本项目建议：**

| 场景               | 选择                              |
| ---------------- | ------------------------------- |
| 只做运动内核 + 简单 API  | 自建轻量 FastAPI 项目结构               |
| 需要后台管理、登录、数据库、前端 | 再考虑 FastAPI Full Stack Template |
| 只做本地仿真 demo      | 可以先不启 FastAPI，只做 Python 包 + CLI |
| 要给 HMI/测试工具读取状态  | 增加 FastAPI API 层                |

结论：

```text
第一阶段采用轻量 FastAPI 结构，不直接套完整 full-stack 模板。
```

---

### 2.2 3D 可视化复用策略

推荐优先使用 **PyVista** 做 3D 可视化。PyVista 官方定位是面向科学计算和工程场景的 Python 3D 可视化与网格分析库，提供 NumPy-native API，并适合作为大型 Python 工具中的可视化层。

**本项目建议：**

| 可视化目标          | 推荐工具                         |
| -------------- | ---------------------------- |
| 3D 装船机姿态显示     | PyVista                      |
| 2.5D 俯视图 + 侧视图 | Matplotlib                   |
| 后续 Web 3D      | Three.js / React Three Fiber |
| 后续更真实工业场景      | Unity / Unreal，暂不建议 MVP 使用   |

结论：

```text
第一版优先 PyVista；如果开发成本过高，立即降级到 Matplotlib 2.5D。
```

---

### 2.3 空间旋转与坐标变换复用策略

空间旋转不要全部手写。推荐优先使用：

1. `numpy`：基础向量、矩阵计算。
2. `scipy.spatial.transform.Rotation`：旋转矩阵、欧拉角、四元数、旋转向量等转换。

SciPy 的 `Rotation` 类用于三维旋转，支持四元数、旋转矩阵、旋转向量、欧拉角等表示，并支持旋转应用、旋转组合、旋转求逆等操作。

也可以参考 `spatialmath-python`，它提供 2D/3D 位姿与方向表达，包括 `SE3`、`SO3`、四元数、位姿组合和点变换等。

`robotics-toolbox-python` 更偏机器人串联机械臂、DH 参数、逆运动学、轨迹规划等完整机器人算法库，本项目的装船机不是标准机械臂结构，暂时不建议直接引入完整 Robotics Toolbox，但可以参考它的设计思想。

**本项目建议：**

| 内容       | 是否自研  | 推荐做法                                 |
| -------- | ----- | ------------------------------------ |
| 向量加减乘除   | 不自研   | 用 `numpy`                            |
| 旋转矩阵     | 尽量不手写 | 用 `scipy.spatial.transform.Rotation` |
| 装船机正运动学链 | 自研    | 因为业务结构是装船机，不是通用机械臂                   |
| 坐标系约定    | 自研    | 必须符合本项目 PRD                          |
| 碰撞检测     | 暂不做   | 后续可看 PyVista / trimesh / pybullet    |

---

### 2.4 配置与数据校验复用策略

推荐使用：

1. `pydantic`：状态结构、命令结构、配置结构校验。
2. `pydantic-settings`：后续读取环境变量、配置文件、命令行参数。

Pydantic Settings 提供从环境变量或 secrets 文件加载配置类的能力。

**本项目建议：**

```text
配置文件 JSON/YAML + Pydantic 模型校验
```

不要直接用散乱的 `dict` 在代码里传来传去，否则后面 API、日志、可视化、测试都会混乱。

## 3. 总体开发阶段

本项目开发拆为 8 个阶段：

| 阶段 | 名称             | 目标                    |
| -- | -------------- | --------------------- |
| M0 | 技术预研与项目骨架      | 确认可复用库，搭建 Python 项目结构 |
| M1 | 基础数据模型         | 定义向量、位姿、配置、状态结构       |
| M2 | 单轴运动内核         | 实现 `MotionAxis` 匀速运动  |
| M3 | 装船机几何与正运动学     | 根据轴值计算关键点坐标           |
| M4 | 仿真世界与状态快照      | 实现时间推进和统一状态输出         |
| M5 | 命令 API 与状态 API | 提供外部调用边界              |
| M6 | 可视化验证          | 实现 3D 或 2.5D 运动展示     |
| M7 | 测试、日志与验收       | 完成单元测试、轨迹记录、验收用例      |

该顺序与 PRD 中推荐的核心开发顺序一致：先实现 `MotionAxis`，再实现几何配置、正运动学、`SimulationWorld`、可视化、命令 API、状态 API、日志和轨迹回放。

#### T3-002：实现 `KinematicsSolver`

**文件：**

```text
app/core/kinematics_solver.py
```

**类：**

```python
KinematicsSolver
```

**方法：**

```python
solve(
    geometry: ShipLoaderGeometry,
    axis_values: dict[str, float]
) -> KinematicsResult
```

**计算链：**

```text
World
  -> Rail travel translation
  -> Base height
  -> Slew rotation
  -> Boom root offset
  -> Boom luff rotation
  -> Boom length + extension
  -> Chute vertical drop
  -> Discharge point
```

PRD 中也建议采用矩阵或向量变换链，而不是手工拼凑零散坐标。

---

#### T3-003：实现基座位置计算

**输入：**

```text
rail_origin
rail_direction
travel
base_height_m
```

**输出：**

```text
base_position
```

**公式：**

```text
base_position = rail_origin + rail_direction * travel + [0, 0, base_height_m]
```

**验收标准：**

1. `travel = 0` 时，基座在轨道起点上方。
2. `travel = 10` 时，基座沿轨道方向移动 10m。
3. 行走变化会影响后续所有关键点。

---

#### T3-004：实现臂架根部与臂架端点计算

**输入：**

```text
slew
boom_luff
boom_extension
boom_base_offset
boom_base_length_m
```

**输出：**

```text
boom_root_position
boom_tip_position
boom_direction
```

**验收标准：**

1. `slew` 变化时，臂架端点 XY 坐标变化。
2. `boom_luff` 增大时，臂架端点 Z 坐标增大。
3. `boom_extension` 增大时，臂架端点远离臂架根部。
4. `boom_total_length = boom_base_length_m + boom_extension`。

---

#### T3-005：实现溜筒与落料点计算

**输入：**

```text
boom_tip_position
chute_length_m
chute_rotate
discharge_offset
```

**输出：**

```text
chute_top_position
chute_bottom_position
chute_direction
discharge_point
```

**当前人工确认：**

```text
溜筒只绕竖直轴旋转。
```

**第一版处理：**

1. `chute_top_position = boom_tip_position`
2. `chute_bottom_position = chute_top_position + [0, 0, -chute_length_m]`
3. `chute_rotate` 只影响 `chute_direction`
4. `chute_rotate` 不改变 `chute_bottom_position`

**验收标准：**

1. 臂架端点移动时，溜筒顶部同步移动。
2. 溜筒底部始终在溜筒顶部下方。
3. 溜筒旋转时，方向向量变化。
4. 溜筒旋转时，第一版落料点位置不变化。

## 14. 不建议当前阶段做的事

### 14.1 不建议一开始做完整后台

当前阶段不建议直接上：

1. 用户登录。
2. 数据库权限系统。
3. 管理后台。
4. React 前端。
5. Docker 生产部署。
6. Traefik / HTTPS。
7. 复杂 CI/CD。

这些能力在 FastAPI Full Stack Template 里都有，但当前项目的瓶颈是装船机运动内核，不是后台工程能力。完整模板可以作为后续参考，不应该成为第一阶段主线。

---

### 14.2 不建议过早接 PLC

PRD 已明确本阶段只预留 API 边界，不实现真实 PLC 通讯。

因此不要一开始做：

1. Allen-Bradley 通讯。
2. PLC 标签映射系统。
3. pycomm3 / pylogix 联调。
4. 真实设备读写。
5. PLC 心跳、报警、联锁。

这些都放到 v3.0 外部系统接入阶段。

---

### 14.3 不建议过早做复杂物理仿真

MVP 明确不做复杂动力学、加减速曲线、真实碰撞检测、煤堆、重量、船舱容量等内容。

所以第一版不要做：

1. 液压系统动态。
2. 电机转矩。
3. 结构弹性。
4. 惯性冲击。
5. 碰撞检测。
6. 煤流仿真。
7. 船舱容量计算。

## 18. 当前最终结论

当前开发主线应当是：

```text
先用成熟 Python 工程框架搭项目，
再用 numpy/scipy 做空间计算，
用 Pydantic 管理配置和状态，
用 FastAPI 提供轻量接口，
用 PyVista 或 Matplotlib 做验证，
把主要时间投入 MotionAxis、KinematicsSolver、SimulationWorld。
```

真正需要自研的是：

1. 装船机自由度建模。
2. 装船机正运动学。
3. 多轴同步仿真。
4. 状态快照结构。
5. 落料点轨迹验证。

不需要自研的是：

1. 后端路由框架。
2. JSON 参数校验。
3. 三维旋转底层数学库。
4. 3D 绘图底层引擎。
5. 测试框架。
6. 配置读取框架。

第一阶段最重要的一句话：

```text
不要把时间浪费在通用框架上，把时间集中到“装船机怎么动、坐标怎么算、状态怎么输出”这三个核心问题上。
```
